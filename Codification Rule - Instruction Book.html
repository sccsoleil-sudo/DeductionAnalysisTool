Overview — How the Dashboard Works

The Logistics Master Dashboard reads deduction/claim data from an Excel file (.xlsx or .xls), stores it in a local database, and produces KPI metrics, charts, and management views.

The dashboard has two primary report tabs:

TabReason CodeWhat It Tracks
Shortage Claims R02 Customer deductions for shipping shortages — tracks outcomes: Recovered, Lost, Actual Shortage, Open
Penalties & Fines R16 Compliance penalties (Fill Rate, EDI, DC Charges, Delivery, Commercial) — closed items only
Key rule: Every row in your Excel must have a valid Reason Code (R02 or R16). Rows without a matching reason code will not appear in either tab.

Section 3

Reason Codes

The Reason Code column determines which report tab a row is assigned to. Only the three codes below are recognized.

Reason CodeDashboard TabDescription
R02 Shortage Claims Short-shipped deduction claims from customers. Tracked through Recovered / Lost / Actual Shortage / Open outcomes. This is the primary reporting tab.
R16 Penalties & Fines Compliance-based penalty charges. Categorized by root cause (Fill Rate, EDI, DC Charges, Delivery, Commercial). Only closed R16 rows are counted in penalty analytics.
R17 Supplemental (Amazon only) Potential shortage claims from Amazon. Not a standalone tab — appears as a supplemental KPI card on the R02 view when Amazon is selected in the customer filter.
Important: Reason codes are stored and compared in UPPERCASE. Values like r02 or R 02 (with space) will not match. Ensure no leading/trailing spaces.

R1R2 Dummy PO Recovered Claim resolved via a dummy purchase order arrangement.

Section 5

Reference Key 2 — R16 Penalties & Fines

For R16 rows, Reference Key 2 determines the penalty category. Only closed R16 rows are counted in penalty analytics.

CodeCategory LabelWhen to Use
FR Fill Rate Penalty charged because the order fill rate fell below the contractual threshold.
EDI EDI Penalty for EDI compliance failures (incorrect/late ASN, PO acknowledgement errors, etc.).
PREP DC Charges Distribution centre preparation/handling charges applied by the customer.
SHIP Delivery Delivery compliance penalties — late delivery, wrong carrier, routing violations.
KAM Commercial Commercial/contractual deductions negotiated or agreed at the account level.
blank or unknown Unclassified No recognized code. The amount will appear under "Unclassified" in the penalty category chart.
XXX Excluded Internal noise/offset rows. Excluded from all R16 analytics (equivalent to PMT for R02).
R16 display order: Categories always appear in this fixed order on the dashboard — Fill Rate → EDI → DC Charges → Delivery → Commercial → Unclassified. This order reflects business priority for root-cause analysis.
Open R16 rows: Open R16 rows are completely excluded from all penalty analytics. Only assign R16 to rows once the penalty is confirmed and cleared.
Section 6

Open vs. Closed Logic

Whether a row is "open" (still in dispute) or "closed" (resolved) is determined automatically from two possible columns, in priority order:

PriorityColumnOpen ConditionClosed Condition
1st Clearing Status Value = 1 Value = 0
2nd Clearing Journal Entry Cell is blank / null Cell has a value (journal entry number)
Fallback Neither column present All rows treated as open by default
Best practice: Always include the Clearing Status column. It is the most reliable and explicit way to mark items as open or closed. If you use Clearing Journal Entry instead, ensure it is populated for every closed item and truly blank for every open item (watch out for formula zeros or placeholder text).

Impact of Open/Closed on Calculations

  • Open items contribute to Open (Actionable) in the total exposure. Their Reference Key 2 code does not affect outcome classification.
  • Closed items are classified by their Reference Key 2 → Recovered / Lost / Actual Shortage.
  • Recovery rate is calculated only from closed items and is not affected by how many items remain open.
  • R16 penalties: open rows are completely excluded from all penalty totals and charts.
Section 7

Outcome Classification Rules

Once a row is determined to be closed, the system applies the following classification logic based on Reference Key 2:

R02 Decision Tree

  1. Is the row open? → Count as Open (Actionable). Stop.
  2. Is Reference Key 2 in {"", "PAYBACK", "RET", "RT", "R1R2"}? → Recovered
  3. Does Reference Key 2 start with COM? → Lost
  4. Does Reference Key 2 contain WO? → Lost
  5. Is Reference Key 2 exactly SHO? → Actual Shortage
  6. Anything else? → Unclassified (appears in the Unclassified bucket; review and update)

R16 Decision Tree (closed only)

  1. Is Reference Key 2 in {"", "PAYBACK", "RET", "RT", "R1R2"}? → Recovered
  2. Does Reference Key 2 start with COM? → Lost
  3. Does Reference Key 2 contain WO? → Lost
  4. Otherwise → categorized by penalty category code (FR, EDI, PREP, SHIP, KAM)
User overrides: Analysts can manually override the classification of any item directly in the dashboard's Shortage Management or Penalties Management tab. Overrides are stored in the database and take precedence over the coded value in subsequent uploads.
Section 8

Recovery Rate Calculation

The Recovery Rate shown on the dashboard (and in exported reports) measures how much of the closed claim value has been recovered. Open items are not included.

Recovery Rate = Recovered (closed) ÷ ( Recovered + Lost + Actual Shortage ) × 100
ComponentIncluded?Reason
Recovered (closed)YesDenominator and numerator
Lost (closed)Yes — denominator onlyPart of closed universe
Actual Shortage (closed)Yes — denominator onlyPart of closed universe
Open (Actionable)NoNot yet resolved — excluded to avoid distortion
PMT / Payback offsetsNoExcluded from all KPIs

Example: If closed items = $4.8M recovered, $0.28M lost, $0.03M actual shortage → Recovery rate = 4.8 ÷ (4.8 + 0.28 + 0.03) = 87.7%

Section 10

Amazon R17 — Potential Shortage

R17 rows represent potential shortage claims from Amazon that have been identified but not yet formally charged. They appear as a supplemental card on the R02 dashboard — not a standalone tab.

When R17 Is Shown

The R17 potential shortage card only appears when Amazon is included in the customer filter. The system identifies Amazon rows by either:

  • The Customer Name field contains the word AMAZON (case-insensitive), or
  • The Assignment field contains the customer number 10118507

How to Code R17 Rows

ColumnValue
Reason CodeR17
Customer NameMust include "Amazon" or use customer number in Assignment
Reference Key 2Use same R02 subcategory codes (e.g. SHO, PAYBACK) — R02 labels are applied
R17 rows are never included in R02 shortage totals. They are tracked separately as a forward-looking risk indicator.
Section 11

Baseline vs. Regular Refresh

The dashboard has two upload modes. Understanding the difference is critical to preserving historical comparison data.

Set BaselineUpload & Refresh
Button "Set Baseline" "↑ Upload & Refresh"
What it does Replaces the reference snapshot used to detect new/changed claims Loads latest data and compares it against the existing baseline to identify changes
When to use When starting a new tracking period, after major data corrections, or when setting the initial dataset For routine weekly/monthly updates — the most common upload type
Baseline reset Yes — previous baseline is wiped and replaced No — existing baseline is preserved for comparison
New/Updated/Removed counters Reset to 0 (no comparison at baseline time) Calculated by diffing against baseline

Auto-Baseline by Filename

If your Excel file is named LogisticsMasterV1.xlsx (or any variation with only letters/numbers that spell out logisticsmasterv1), the system will automatically treat the upload as a baseline, regardless of which button was used.

Clear Baseline button: The "✕ Clear Baseline" button in the header erases the current baseline from the database. After clearing, the next upload will become the new baseline automatically (since no prior baseline exists).

What Happens to Missing Rows During a Refresh

  • R02 rows that existed in the baseline but are absent in the new upload are synthesized as cleared — they are added back with is_open=0 and status "Cleared". This prevents them from vanishing from history.
  • Non-R02 rows that go missing are counted as removed.

PMT / Payback Offset Rows

Rows with Reference Key 2 = PMT are payment-offset rows — they represent a negative amount that nets against the gross deduction in the same payment batch.

How PMT Rows Are Handled

WhereTreatment
All KPI totals (Recovered, Lost, Shortage, Open)Excluded
Donut charts and bar chartsExcluded
Header KPI — "Total Received Claim"Excluded (gross total of non-PMT lines shown)
Header — "Identified Payback (excluded)" notePMT total amount shown as an informational footnote
Do not use PMT as a general code. It is a system-reserved exclusion code. Only SAP-generated payment offset entries should carry PMT. Using it for other purposes will cause those rows to disappear from all dashboard metrics.

Section 14

Upload Workflow — Step by Step

Routine Monthly Update (most common)

  1. Export your latest claims data from SAP as an .xlsx file.
  2. Verify column names match those listed in Section 2.
  3. Ensure Reason Code values are R02, R16, or R17 in uppercase.
  4. Ensure Reference Key 2 uses only the approved codes from Sections 4 and 5.
  5. Ensure Clearing Status is 1 (open) or 0 (closed) for every row.
  6. Click "↑ Upload & Refresh" in the dashboard header.
  7. Select your file. The dashboard will update automatically.

Initial Setup / Baseline Reset

  1. Prepare your full historical dataset as an .xlsx file.
  2. Click "Set Baseline" in the dashboard header (or name the file LogisticsMasterV1.xlsx and use "Upload & Refresh").
  3. Confirm the baseline name appears in the top-right of the header after upload.
File format: Both .xlsx (Excel 2007+) and .xls (Excel 97–2003) are supported. CSV files are not supported.
Section 15

Common Mistakes & FAQs

Q: My total on the dashboard doesn't match my spreadsheet total.

Check these common causes:

  • You are filtering by year or division — remove all filters and compare again.
  • Rows with Reference Key 2 = PMT are excluded from the main total but shown in the "Identified Payback" note.
  • R17 rows are not included in R02 totals.
  • R16 open rows are excluded from all R16 totals.

Q: My Recovery Rate looks wrong — it's too low.

  • Recovery rate only uses closed items. A large number of open items will not reduce the rate — they are excluded.
  • Verify items you expect to be "Recovered" have a blank, PAYBACK, RET, RT, or R1R2 Reference Key 2 and are actually closed (Clearing Status = 0).

Q: Items are not appearing in any chart.

  • Check that Reason Code is exactly R02 or R16 (uppercase, no spaces).
  • Check that Journal Entry Date is a valid date. Rows with unparseable dates may be excluded from date-filtered views.

Q: An item appears as "Unclassified".

The Reference Key 2 value does not match any recognized code. Options:

  • Correct the code in the Excel file and re-upload.
  • Use the manual override feature in the Shortage Management tab to reclassify the item directly in the dashboard.

Q: What happens if I upload the same file twice?

The system uses a business key (combination of Customer Name, Assignment, Payment Reference, Invoice Reference, Reason Code, Journal Entry, and Amount) to identify unique rows. Duplicate uploads will overwrite existing rows with the same key — no duplicate entries will be created.

Q: Can I have multiple sheets in my Excel file?

Yes. All sheets are concatenated into a single dataset. Ensure all sheets use the same column names (including capitalization).

Q: Why does the "Clear Baseline" button erase my history?

It only clears the baseline reference snapshot used for change detection (new/updated/removed row counts). It does not delete your current live data. After clearing, the next upload will become the new baseline.
